# Code Workbench

- Keep all Apple binary interpretation and planning in `crates/binary/inspection`.
- Keep WIT and component bindings in `crates/workbench/component`; the core must remain an ordinary Rust library.
- Define ordinary Rust APIs first; every consumer-facing domain operation exported by a component must map to one of those APIs. Expose only selected operations through WIT adapters, keep required functions and target-compatible dependencies internal, and import deliberately external capabilities through explicit interfaces. Modules and crates do not determine component boundaries; do not export helpers merely because they are reachable or expose WIT types in ordinary Rust APIs. Keep direct Rust calls where no external boundary is needed. Component composition does not supply cross-process transport.
- Rust-only operation is mandatory: the complete implemented non-UI workflow must work through Rust libraries and Rust platform adapters without TypeScript, JavaScript, Node, jco or a Wasm runtime. Follow [Rust reuse across execution environments](docs/architecture/rust-runtime-independence/README.md) when planning, implementing or reviewing changes. Compile the same reusable Rust behavior for browser Wasm and native use; platform adapters may differ.
- Use jco as the default React-to-Wasm component binding. Inside that component, the ordinary Rust analyzer calls the ordinary Rust filesystem client, which imports upstream Polymorph WebSocket operations. Bind the published Polymorph browser provider with only the necessary jco ABI/resource-value conversion; do not implement another browser socket or filesystem protocol in TypeScript. Client and service share ordinary Rust filesystem messages directly over WebSocket. Fetch upstream Polymorph WIT unchanged through the pinned `wkg` workflow. Follow [the filesystem communication flow](docs/architecture/rust-runtime-independence/filesystem-communication-flow.md).
- Keep reusable filesystem-client protocol, resource ownership, response validation and completion semantics in Rust outside the analysis core. TypeScript supplies presentation and environment-required bindings. The application component and native service share their address through `config/native_service.rs`; frontend code neither configures nor stores it. Optional probe APIs retain explicit endpoints.
- Outside presentation and UI lifecycle, TypeScript/JavaScript is permitted only for environment-required binding or host API access, such as browser networking and component value conversion. It must not supply or duplicate analysis, filesystem-client protocol or workflow semantics that Rust relies on. Boundary-local safety checks remain required where appropriate; Rust must independently enforce its own contracts. Document why each host binding is necessary.
- In-process Rust use must not require JavaScript, Node, jco, Wasm, a service or RPC. Keep transport and runtime dependencies in adapters. Reuse qualified libraries; do not create speculative abstractions or rewrite unrelated adapters as part of a small change.
- For affected behavior, identify its Rust owner, platform dependencies, unsupported capabilities and validation across supported execution modes. Test shared semantics without JavaScript and qualify real adapters before claiming cross-runtime support; report untested modes and unsupported capabilities explicitly.
- Follow the [testing policy](docs/architecture/testing-policy.md) when adding, reviewing, simplifying or removing tests. Use it as the baseline for deciding what to test and what not to test.
- Reference repositories outside this project are read-only.
- Run `pnpm engine:build` after Rust, WIT or component-binding changes. Run appropriate native/component tests, typecheck and the production build before delivery.
- Read the installed Next.js guides under `apps/web/node_modules/next/dist/docs` before changing App Router behavior. Use Base UI primitives where appropriate.
- Keep component runtime ownership independent of presentation components. `useNativeSession` owns the runtime returned by `createNativeRuntime` and exposes `getNativeSession` to the model. The runtime’s `getSession()` lazily initializes and caches the component's generated WIT `Session`; the model calls its methods directly. Keep `AsyncSession` as a mapped generated type for JSPI promises rather than maintaining a second operation API. Let jco control component export entry, and keep the model's synchronous `beginOperation` guard for UI interaction. Follow the [runtime lifecycle contract](docs/architecture/system-overview.md#runtime-lifecycle) for host disposal and retained session references. Reusable Rust and browser APIs must not depend on the number or lifetime of UI variants. Do not introduce application React Context, a global singleton or a shared runtime store.
- Keep the Base UI baseline while evaluating Ark/Panda. The page's `WorkbenchShell` owns one component runtime and one `useWorkbenchModel` model. `/`, `/?view=ark` and `/?view=compare` select presentations of that same model. Keep the shell unkeyed when its view changes; the root layout owns page structure only. Pass the model explicitly to presentations; both comparison panes share operation feedback, the current report and its architecture tab. The hook forwards intent and displays Rust-composed outcomes. A full page refresh creates a new owner that queries the retained native selection; switching presentations neither initializes nor disposes the runtime. Analysis uses `Session::inspect` without progress notifications, cancellation controls or signals. The UI shows a pending state until the invocation returns its outcome; do not add replacement polling or events. Native selection survives inspection, disconnect and navigation until successful replacement or owner/service shutdown. Preserve native-dialog Cancel and service shutdown/late-acquisition guards. Do not add a frontend deselection action or remote cleanup API.
- Scope Panda tokens to `.ark-theme`, keep its preflight disabled, and preserve Base UI control styles. Edit recipes/configuration rather than generated `apps/web/styled-system` files.
- Do not treat signature-command presence as signature validity or execution eligibility.
- Application input uses native Rust selection and bounded reads. Do not add browser File/Blob acquisition, sample loading or JavaScript filesystem providers. Wasm asset fetching and networking buffers remain environment bindings. Native dialogs belong in the service executable.
- Do not add signing, uploads or deployment without task scope requiring them.
