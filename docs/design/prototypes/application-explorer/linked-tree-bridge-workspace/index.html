    Why separate the layers?

    Automatic tree highlighting · separate copy

    The approved original is preserved. In this copy, a new file or architecture selection opens the branches containing its internal incoming sources and outgoing targets. The current file stays blue; incoming sources are teal with IN labels; outgoing targets are purple with OUT labels.

    Previewing a bridge card automatically opens and scrolls its other endpoint into view in the tree, with a stronger outline. This changes neither the selected file nor keyboard focus. Manual collapse is respected until a new selection or an explicit relationship preview. A neutral +count marks hidden related descendants; it does not make the ancestor a relationship endpoint.

    System and unresolved references have no corresponding file row. Planning suggestions are excluded from automatic target marks, but can still be revealed explicitly through the inspector. Back restores the earlier expansion, preview, selected file and tree scroll position.

    The selected file has four bridges. Horizontal connections stay within the visible Atlas.app inventory. Vertical connections hold system names, external paths and references whose containment is still unknown.

    Bridge Direction Meaning
    West Resource → selection Internal ingress: helper, executable alias, metadata or resource records.
    East Selection → resource Internal egress: bundle targets and labelled candidates.
    North External source → selection Only evidenced incoming external associations. This example has no such inventory.
    South Selection → reference System libraries, external paths, capabilities and unresolved names.

    Resolution context has no graph port

    The vertical inspector at the far right explains the active connection. It never receives an arrow. The selected resource appears once in the graph; inspecting an incoming relation cannot create a second target node for that same file.

    Paths do not determine the axis by their spelling

    @rpath/libTelemetry.dylib has an internal candidate in this example, so its resource endpoint is east. @rpath/Optional.dylib has no target, so it remains south with containment unknown. The original load name and runpath context remain visible in the inspector. A proposed replacement for an absolute /Original/… path is a planning suggestion, not an internal resolution.

    Try the original application's richer neighborhood

    Select Example: Render Helper and the executable alias enter from the west; framework metadata, libTelemetry and application settings leave to the east. The system library and unresolved optional dependency leave south. Select a connection to inspect it, Reveal to locate its other endpoint, or Focus to recenter. Back restores the prior exploration.

    Scope is the outer Atlas.app inventory. A resource elsewhere in Atlas.app is still internal even when outside Example.framework. Each card identifies its immediate bundle. Collapsing the physical tree never changes graph geometry.

    Evidence and implementation limits

    All data is authored for this design study. Candidate dependencies, path mentions, aliases and declarations retain their own evidence labels. These are not observed file accesses, successful loads or verified signature states. Empty external ingress means no records were supplied, not that no external consumers exist.

    This file uses only HTML, CSS and presentation JavaScript. The ordinary Rust core remains unchanged; actual binary interpretation and planning belong under crates/binary/inspection. No resolver, filesystem acquisition, React, Wasm or service integration is added.
